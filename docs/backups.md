# Резервное копирование и проверка восстановления

Инструменты работают с запущенными сервисами `web` и `db` Docker Compose.
По умолчанию выбирается локальная среда; флаг `--production` явно выбирает
отдельный проект `family-production` из `compose.production.yaml`.
На компьютере требуется Python 3.11 или новее. Команды выполняются из корня проекта.

С 22 сентября копия включает семейные медиа, фотографии личных воспоминаний
и аватары личных профилей, включая закрытые материалы и черновики.
Проверка восстановления поддерживает и старые копии без таблиц личного раздела.

## Зашифрованная плановая копия

```sh
python3 scripts/secure_backup.py create --daily
```

Результат — новый файл `backups/encrypted/fks-<дата>-<идентификатор>.tar.age`,
содержащий базу, медиа и манифест. Все новые плановые копии используют этот режим.
Повторный запуск за ту же дату по Москве проверяет контрольную сумму и пропускает
создание дубликата. Если файл потерян или повреждён, создаётся новая копия.
Одновременные запуски защищены блокировкой. Старые копии автоматически не удаляются.

Для шифрования установлен [age v1.3.2](https://github.com/FiloSottile/age/releases/tag/v1.3.2)
в `.tools/age-v1.3.2/`. Установщик `python3 scripts/install_age.py` сверяет
контрольную сумму официального архива; он поддерживает macOS arm64 и x86_64.
Для нового компьютера ключи можно создать командой `python3 scripts/secure_backup.py init`.
Уже существующий ключ при повторном запуске не заменяется.

Открытый ключ находится в `secrets/backup-recipient.txt`. Этого файла достаточно
для создания копий. Для восстановления необходим **исходный** ключ
`secrets/backup.agekey`; заново сгенерированный ключ старые копии не расшифрует.
Ключ нужно сохранить отдельно от копий. Содержимое ключей не выводится в журнал.
Ключи, инструменты и копии исключены из Git, файлы копий и ключей имеют права `600`.

При обычном завершении, в том числе обработанной ошибке, временные
незашифрованные файлы удаляются. Аварийное выключение компьютера может оставить
временную папку `.secure-*`; автоматическая очистка старых папок не выполняется.
Ранее созданная ручная незашифрованная копия сохраняется отдельно.

Проверка расшифровки и полного восстановления:

```sh
python3 scripts/secure_backup.py verify backups/encrypted/fks-<дата>-<идентификатор>.tar.age
```

Файл целиком проверяется age до начала восстановления. Затем используется
одноразовая база и отдельная папка медиа, как описано ниже. Можно указать другой
путь к исходному ключу через `--identity /путь/к/ключу`.

## Копии production

После [подготовки и запуска production](operations.md#режимы-запуска):

```sh
python3 scripts/secure_backup.py create --production --daily
```

Результат сохраняется отдельно от локальных копий:
`backups/production/encrypted/fks-<дата>-<идентификатор>.tar.age`.
Для ручной незашифрованной копии используется `python3 scripts/backup.py create --production`;
её каталог по умолчанию — `backups/production/`. Оба режима принимают `--output`.
Флаг выбирает уже запущенный стек, но не разворачивает сервер и не переносит данные.

Используется файл `production.env`. Если стек запущен с другим файлом,
задайте тот же путь в `FKS_PRODUCTION_ENV_FILE` при копировании. База и медиа
снимаются из одного выбранного проекта. В манифест добавляется контекст источника:
каталог проекта, параметры Compose, путь к файлу окружения и отпечаток выбранного
Docker-сервера, но не содержимое окружения, адрес подключения или пароли.

Используются существующие ключи из `secrets/`; менять или создавать их заново
для этого режима не нужно. Установщик age пока рассчитан только на macOS;
подготовку инструментов и ключей на будущем сервере нужно выполнить отдельно.
Копии остаются на компьютере, где запущена команда, и автоматически никуда
не отправляются.

Проверка production-копии также использует одноразовое окружение:

```sh
python3 scripts/secure_backup.py verify backups/production/encrypted/fks-<дата>-<идентификатор>.tar.age
```

При `--daily` копия другой среды не считается выполненной копией текущей,
даже если явно задан общий каталог. Переключение Docker-сервера, изменение
параметров Compose или пути к production-окружению также требует новой копии.
Для определения источника Docker должен быть доступен даже при повторном запуске;
если источник нельзя подтвердить, операция останавливается с ошибкой.
Старые отметки ежедневного запуска без отпечатка источника не используются:
создаётся новая копия, а прежние файлы сохраняются. Изменения содержимого файла
окружения по прежнему пути и замена базы/томов внутри того же проекта
не отслеживаются: после перенастройки источника запускайте команду без `--daily`,
чтобы принудительно создать новую копию.
Не переключайте Docker-контекст и не меняйте настройки источника во время
копирования: проверки до и после снимка обнаруживают смену источника,
но не заменяют неизменную конфигурацию на время операции.

Выбор среды и защита от ошибочного пропуска проверены автоматическими тестами
на искусственных данных. 20 сентября 2026 года свежая production-копия успешно
расшифрована и полностью восстановлена в изолированной среде: 31 таблица и
1 медиа-файл совпали с манифестом. Рабочая база не изменялась.

## Расписание

7 сентября 2026 года в Codex настроена еженедельная задача
«Еженедельная зашифрованная копия семейного архива» на понедельник,
09:00 по Москве.
Она выполняет `python3 scripts/secure_backup.py create --daily` в этом проекте.
Это по-прежнему копия локальной среды: появление `--production` не меняет расписание
и не переключает его источник. Для будущего сервера расписание настраивается отдельно.
Компьютер, приложение Codex и Docker должны быть запущены; запуск также зависит
от доступных лимитов и разрешений Codex. Это локальная задача приложения,
а не серверный планировщик. [Условия локального запуска](https://learn.chatgpt.com/docs/automations?surface=app).

Пользователь выбрал хранение только на этом компьютере. Перенос во внешнее
хранилище, сроки хранения и автоматическое удаление старых копий не настроены.

## Ручная копия без шифрования

```sh
python3 scripts/backup.py create
```

Результат — новая папка `backups/fks-<дата>-<идентификатор>/`:

- `database.dump` — снимок таблиц схемы `public` PostgreSQL, включая пользователей,
  приглашения, приватность, источники и журнал действий;
- `media.tar` — все файлы, на которые ссылаются записи `MediaAsset`, включая
  архивированные и отклонённые; файлы без записи в базе не включаются;
- `manifest.json` — версия формата, образ PostgreSQL, количества записей и
  контрольные суммы базы, архива и каждого медиа-файла.

Каждая копия получает новое имя. Папка доступна только владельцу, файлы имеют
права `600`. Незавершённая копия не публикуется и удаляется при обработанной ошибке.
Каталог `backups/` и файлы `*.dump` исключены из Git.

На время снимка и копирования медиа блокируется запись в таблицы; чтение остаётся
доступным. Уже начатые изменения должны завершиться. Если блокировка не получена
за 5 секунд, создание копии прекращается, и его можно повторить в менее загруженное
время. Для согласованности используется один экспортированный снимок PostgreSQL.
Не запускайте миграции и не меняйте файлы вручную во время копирования.

Отсутствующий файл, символическая ссылка или ошибка копирования прерывают операцию.
Дамп ограничен четырьмя минутами; инструмент рассчитан на текущий небольшой архив.
Для большой базы нужен отдельный эксплуатационный процесс копирования.

Другой каталог можно указать через `--output /путь/к/защищённому/каталогу`.
Для него исключение из Git и защита носителя должны быть настроены отдельно.

## Проверка восстановления

Подставьте папку, которую напечатала команда создания:

```sh
python3 scripts/backup.py verify backups/fks-<дата>-<идентификатор>
```

Проверка сверяет контрольные суммы, извлекает медиа во временную папку и запускает
новый PostgreSQL из того же локального образа. У временного контейнера нет сети,
опубликованных портов и подключённых каталогов проекта. Рабочая база не является
целью восстановления.

Дамп полностью загружается в новую базу с проверкой ошибок. Затем сравниваются
количества записей всех таблиц, список файлов в восстановленной базе и байты
восстановленных медиа. Успешное завершение подтверждает пригодность этой копии
для восстановления данных, но не заменяет браузерную проверку всего приложения.

После проверки временный контейнер и его том, а также извлечённые файлы удаляются.
Сама резервная копия сохраняется. При аварийном завершении компьютера временный
контейнер с именем `fks-restore-check-…` может остаться: перед ручным удалением
обязательно проверьте его точное имя. Не удаляйте том `postgres_data`.

## Хранение и восстановление после сбоя

Копия содержит приватные семейные данные, хеши паролей и токены приглашений.
Команда `backup.py create` не шифрует её; `secure_backup.py create` добавляет
шифрование. Контрольная сумма обычной копии выявляет повреждение, но не подтверждает
подлинность: проверяйте только доверенные копии. Хранение на том же компьютере
не защищает от потери самого компьютера или диска.

Окружение `.env`, секреты, исходный код и образ приложения в копию не входят.
Их нужно сохранять отдельно безопасным способом. Образ PostgreSQL, записанный в
манифесте, должен быть доступен локально: проверка сама не загружает образы из сети.

Инструмент автоматически выполняет только восстановление в одноразовом окружении.
Перенос проверенной копии в рабочее окружение должен выполняться как отдельная
операция с сохранением текущей базы, согласованием остановки приложения и проверкой
совместимости кода и миграций. Команды перезаписи рабочей базы намеренно отсутствуют.
