# Проверка работоспособности локального проекта

```sh
docker compose ps
docker compose exec -T web python manage.py healthcheck
docker compose exec -T web python manage.py media_storage_report
```

Команда `healthcheck` подключается по HTTP к `127.0.0.1:8000/health/`
внутри контейнера с тайм-аутом 3 секунды. Это проверяет реально запущенный сайт.
Обработчик сайта выполняет `SELECT 1` в базе и возвращает только общий статус:
`200 {"status":"ok"}` или `503 {"status":"unavailable"}`. Ответ не кешируется
и не содержит данных семьи, имён серверов или текста ошибки базы.

Команда завершается ошибкой при остановленном или зависшем сайте, ошибке базы,
перенаправлении вместо ответа или некорректном ответе. Она использует настроенный
Host и заголовок доверенного HTTPS-прокси для обычной схемы reverse proxy.
В режиме Funnel внутренняя проверка сначала передаёт служебную запись PROXY v2
по loopback-соединению; внешние HTTP-заголовки не определяют HTTPS.

В Docker Compose проверка назначена каждые 30 секунд с тайм-аутом 5 секунд,
стартовым периодом 15 секунд и тремя попытками. Стартовый период — время,
в течение которого начальные ошибки не учитываются, а не задержка первого запроса.
После трёх учитываемых ошибок Docker помечает контейнер `unhealthy`.
Это не перезапускает контейнер автоматически и не отправляет отдельное уведомление.

6 сентября 2026 года настройки применены к локальному контейнеру `family_web`;
Docker подтвердил состояние `healthy`. Отчёт закрытого хранилища подтвердил
2 зарегистрированных файла без отсутствующих файлов, файлов без записи и ссылок.

## Режимы запуска

Обычный `compose.yaml` остаётся средой локальной разработки: исходный код
подключается с компьютера, а сайт запускается встроенным сервером Django.

Для размещения подготовлен отдельный `compose.production.yaml`. Его образ запускает
Gunicorn от непривилегированного пользователя, собирает статические файлы при
сборке и отдаёт их через WhiteNoise. Файловая система контейнера доступна только
для чтения; запись разрешена во временный каталог и отдельный постоянный том
закрытых семейных файлов. Контейнеру запрещено получать новые привилегии, а все
Linux capabilities удалены.

Перед первым запуском скопируйте `production.env.example` в локальный
`production.env`, замените все значения-заглушки и выполните:

```sh
docker compose -p family-production -f compose.production.yaml build web
docker compose -p family-production -f compose.production.yaml run --rm web python manage.py check --deploy --fail-level WARNING
docker compose -p family-production -f compose.production.yaml run --rm web python manage.py migrate
docker compose -p family-production -f compose.production.yaml up -d
docker compose -p family-production -f compose.production.yaml exec -T web python manage.py healthcheck
```

Это строгая проверка: начальный профиль Funnel с HSTS на один час, без
includeSubDomains/preload, также сообщает `security.W005` и `security.W021`.
Они относятся к выбранному начальному HSTS-профилю, а не к отсутствию HTTPS.
В изолированном тесте 12 сентября они рассмотрены отдельно; почта там намеренно
dummy и сообщает `config.W001`. Реальный запуск с отправкой писем требует
устранить почтовые предупреждения и подтвердить доставку. Не подавляйте все
предупреждения ради прохождения команды.

Отдельное имя проекта `family-production` отделяет контейнеры и тома от локальной
разработки. Development использует порт `8000`, production — `18080`;
оба доступны только локально согласно фактическим привязкам контейнеров.
Production начинает с отдельной базы и отдельного хранилища: существующие
семейные данные автоматически не переносятся. Инструменты резервного копирования
поддерживают выбор этой среды через `--production`; [команды и ограничения](backups.md#копии-production).
От переноса старых тестовых данных пользователь отказался; production начат
с отдельной базы. 20 сентября свежая production-копия полностью восстановлена
в изолированной среде (31 таблица, 1 файл). Расписание production-копий
и уведомления о сбоях ещё нужно настроить.

`production.env` исключён из Git. Production-контейнер доступен только через
`127.0.0.1:18080`; это отдельный порт, чтобы не перепутать его с локальным
сервером разработки на `8000`.
Access log Gunicorn отключён, потому что адреса принятия приглашений и
восстановления пароля содержат одноразовые токены. Ошибки приложения продолжают
поступать в журнал контейнера без сохранения содержимого файлов.

### Бесплатный внешний адрес через Tailscale Funnel

Для выбранного адреса `web-family.tail7fe668.ts.net` Funnel должен принимать
HTTPS на порту `8443`, завершать TLS и передавать запросы в production через
PROXY v2. В этом режиме Gunicorn получает настоящий адрес телефона, а приложение
помечает запрос HTTPS только после проверки служебной записи:

```sh
tailscale funnel --tls-terminated-tcp=8443 --proxy-protocol=2 tcp://127.0.0.1:18080
```

Перед этим убедитесь, что в `production.env` заданы `DJANGO_PROXY_PROTOCOL_ENABLED=True`,
`GUNICORN_PROXY_PROTOCOL=v2`, а в `GUNICORN_PROXY_ALLOW_IPS` — `127.0.0.1`
для внутреннего healthcheck и **наблюдаемый адрес отправителя** в production-сети.
Адрес её шлюза можно посмотреть как подсказку:

```sh
docker network inspect family-production_default --format '{{(index .IPAM.Config 0).Gateway}}'
```

Перед добавлением подтвердите адрес настоящим соединением: на Docker Desktop
он зависит от сети. В изолированной проверке 12 сентября наблюдался `172.19.0.1`,
но переносить это значение в другую сеть нельзя. С `127.0.0.1` как единственным
доверенным адресом healthcheck работает, а пробный PROXY-запрос с Mac получает
403; журнал тестового Gunicorn показывает фактический адрес отклонённого отправителя.
Укажите подтверждённый адрес вместе с `127.0.0.1`, затем пересоздайте только `web`.
Символ `*`, подсети и неверный формат запрещены при старте Gunicorn и проверке
конфигурации. Не открывайте порт `18080` на LAN или в интернет.

Gunicorn 26.2.0 передаёт в WSGI значение `TCP4`/`TCP6`, а не версию протокола.
Middleware требует эти метаданные и достоверный IP, отклоняет обычный HTTP с 403,
удаляет заголовки переадресации и задаёт HTTPS через WSGI. Доверие Gunicorn к
HTTP-заголовкам отключено. Повторное использование соединения отключено, поскольку
эта версия Gunicorn не переносит PROXY-метаданные на следующий запрос соединения.

После запуска откройте
`https://web-family.tail7fe668.ts.net:8443/health/` с телефона через мобильную
сеть. Должен быть только ответ `{"status":"ok"}`; семейные данные на этом
адресе до завершения переноса публиковать нельзя. Для постоянного запуска
добавляется `--bg` только после успешной проверки. Временный запуск останавливается
Ctrl+C. Для постоянного маршрута сначала проверьте `tailscale funnel status --json`,
затем отключите только выбранный порт командой
`tailscale funnel --tls-terminated-tcp=8443 off`; глобальный `reset` не нужен.

### Локальная сборка при недоступности Docker Hub

12 сентября обычная сборка вновь остановилась на получении метаданных
`python:3.14-slim`. `Dockerfile.local-cache` собрал актуальный код и статику
на ранее проверенном локальном образе проекта. До сборки проверены Python 3.14,
все точные версии из `requirements.txt`, бинарное дополнение psycopg и `pip check`.
Старый `/app` удаляется только внутри создаваемого образа, затем копируются текущие
исходники. Семейные файлы, SQLite, секреты и отчёты исключены из контекста.

```sh
docker build --network=none -f Dockerfile.local-cache -t family-knowledge-system-web:funnel-candidate .
```

Это новая сборка приложения с прежними зависимостями и системными пакетами,
а не обновление базовой ОС из реестра. Она предназначена для этого Mac:
унаследованные слои старого образа не очищаются физически, поэтому образ
нельзя отправлять в реестр или передавать другим людям. Обычный `Dockerfile`
сохраняется для чистой сборки при восстановлении доступа к реестру.
Рабочие контейнеры и тег `latest` этой командой не заменяются.

7 сентября 2026 года production-запуск проверен отдельным smoke-тестом:
Gunicorn 26.2.0 запустил два worker-процесса, endpoint работоспособности ответил
`ok`, а версионированный CSS был отдан WhiteNoise с долгим immutable-кешем.
Docker подтвердил запуск от пользователя `family`, файловую систему только для
чтения и удаление всех Linux capabilities.

После добавления «Моих изменений» образ собран заново и проверен во временном
контейнере без опубликованных портов. Подтверждены входная страница, CSP,
актуальный CSS и ответ работоспособности. Непривилегированный пользователь
успешно записал, прочитал и удалил искусственный файл в отдельном пустом томе
закрытого хранилища; рабочие семейные файлы не подключались. Временное окружение
удалено. Это проверка образа, а не размещение публичного сервера.

10 сентября браузерный сценарий обнаружил вставку встроенных CSS внутри
`vis-network`: стили извлечены в отдельный локальный файл, строгая CSP сохранена.
Повторная полная сборка после этого изменения не завершилась из-за тайм-аута
реестра Docker; повтор 11 сентября завершился той же ошибкой. Перед размещением
её нужно повторить. Локальные проверки
выполнялись с актуальными исходниками и зависимостями уже установленного образа.
Сборка статики WhiteNoise, включая новый CSS, отдельно прошла во временной папке
изолированного контейнера; эта папка удалена после проверки.

11 сентября в отдельной среде прошли 222 теста Django и полный браузерный сценарий
приглашения, модерации, закрытых PNG/PDF и отзыва доступа; отдельно прошли 30 тестов
инструментов. Проверка включает запрет кеширования ответов с закрытыми файлами.
Тестовый сайт ответил `ok`. Временные контейнеры и данные удалены; команды запуска
или остановки рабочего проекта не выполнялись. Финальная проверка Docker показала
рабочие `web` и `db` как `healthy`.
Это проверка текущих исходников с зависимостями кешированного образа,
а не подтверждение новой сборки или публичного размещения.
Отчёты и повторение — в [браузерной проверке](browser-checks.md).

В настройках явно заданы HttpOnly для cookie сессии, SameSite=Lax для cookie
сессии и CSRF, запрет iframe, MIME sniffing и междоменных opener-связей.
Значения разрешённых хостов и HSTS настраиваются через окружение. Эти настройки
и production-контейнер сами по себе не создают HTTPS-сервер и не подтверждают
готовность к публичному запуску.

Зашифрованные копии и проверка восстановления описаны в `docs/backups.md`.

## Восстановление пароля

На странице входа доступна ссылка «Забыли пароль?». Пользователь указывает
email и получает одинаковое подтверждение независимо от того, зарегистрирован
ли этот адрес. Для активного аккаунта при доступном лимите отправляется одноразовая ссылка;
после открытия токен удаляется из адресной строки, а срок его действия — один
час. Новый пароль проверяется стандартными валидаторами Django. Приостановленные,
отключённые и приглашённые, но ещё не активированные аккаунты письма не получают.

Частота запросов ограничена: 5 запросов с подключения и 3 попытки доставки
на один email за 15 минут. Статус пользователя повторно проверяется при
применении ссылки; конкурентная смена пароля по одной ссылке защищена
транзакцией и блокировкой пользователя. Правила и ограничения описаны
в [восстановлении пароля](password-recovery.md).

Текущий локальный режим использует консольную доставку писем: содержимое выводится
в журнал контейнера, а внешняя SMTP-доставка ещё не настроена. Перед публичным
запуском требуется подключить SMTP или другой доверенный провайдер и проверить
DNS-аутентификацию домена (SPF, DKIM, DMARC).

Параметры SMTP включены в `production.env.example`. Проверка `check --deploy`
показывает предупреждение для локальных почтовых режимов, адресов-заглушек,
отсутствия шифрования и неизвестного почтового backend; несовместимые режимы
STARTTLS/SSL и некорректный тайм-аут считаются ошибками. Флаг
`--fail-level WARNING` делает предупреждения причиной остановки проверки.
Проверка не соединяется с провайдером и не подтверждает доставку. Инструкция
подключения — в [восстановлении пароля](password-recovery.md#подключение-почты).

После усиления восстановления пароля полный набор из 191 теста прошёл успешно
одним последовательным запуском, включая конкурирующие запросы на PostgreSQL.
Новая миграция для этого этапа не требуется.

## Локальные сценарии и политика загрузки ресурсов

Библиотека семейного дерева `vis-network` закреплена на версии 10.1.2 и хранится
в статических файлах приложения вместе с лицензиями MIT и Apache 2.0. Браузеру
больше не требуется обращаться к внешнему CDN для отображения дерева.

Встроенная CSP-защита Django разрешает JavaScript только с адреса самого сайта
и из шаблонных блоков с одноразовой меткой текущего ответа. Встроенные обработчики
событий запрещены; загрузка объектов и встраивание сайта во фрейм также запрещены.
Стили перенесены в локальный `family.css`: встроенные блоки и атрибуты стилей
запрещены политикой и контролируются отдельным тестом шаблонов.

После полного запрета встроенных сценариев и стилей и подготовки production-режима
набор из 203 тестов прошёл успешно. Локальный сервер
возвращает политику в заголовке ответа, а закреплённый файл библиотеки дерева
доступен из статического каталога приложения. Новая миграция не требуется.
