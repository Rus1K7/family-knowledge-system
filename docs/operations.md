# Проверка работоспособности локального проекта

```sh
docker compose ps
docker compose exec -T web python manage.py healthcheck
docker compose exec -T web python manage.py media_storage_report
```

Команда `healthcheck` подключается по HTTP к `127.0.0.1:8000/health/`
внутри контейнера с тайм-аутом 3 секунды. Это проверяет реально запущенный сайт.
Обработчик сайта выполняет `SELECT 1` в базе и возвращает только общий статус:
`200 {"status":"ok"}` или `503 {"status":"unavailable"}`. Ответ не кешируется
и не содержит данных семьи, имён серверов или текста ошибки базы.

Команда завершается ошибкой при остановленном или зависшем сайте, ошибке базы,
перенаправлении вместо ответа или некорректном ответе. Она использует настроенный
Host и заголовок доверенного HTTPS-прокси для внутреннего запроса; перенаправление
на HTTPS для обычных HTTP-запросов остаётся включённым в production.

В Docker Compose проверка назначена каждые 30 секунд с тайм-аутом 5 секунд,
стартовым периодом 15 секунд и тремя попытками. Стартовый период — время,
в течение которого начальные ошибки не учитываются, а не задержка первого запроса.
После трёх учитываемых ошибок Docker помечает контейнер `unhealthy`.
Это не перезапускает контейнер автоматически и не отправляет отдельное уведомление.

6 сентября 2026 года настройки применены к локальному контейнеру `family_web`;
Docker подтвердил состояние `healthy`. Отчёт закрытого хранилища подтвердил
2 зарегистрированных файла без отсутствующих файлов, файлов без записи и ссылок.

## Текущие ограничения эксплуатации

Сейчас используется локальный Django development server. Публичное развёртывание
через production-сервер и HTTPS-прокси ещё не выполнено.

В настройках явно заданы HttpOnly для cookie сессии, SameSite=Lax для cookie
сессии и CSRF, запрет iframe, MIME sniffing и междоменных opener-связей.
Значения разрешённых хостов и HSTS настраиваются через окружение. Эти настройки
сами по себе не создают HTTPS-сервер и не подтверждают готовность к публичному запуску.

Зашифрованные копии и проверка восстановления описаны в `docs/backups.md`.

## Защита входа

6 сентября 2026 года включено ограничение частоты попыток для обычного
и административного входа: 5 попыток на сочетание подключения и имени,
30 суммарно на подключение за 15 минут. Окна общие для обоих входов
и всех процессов сайта; учитываются в том числе успешные попытки.
Существующие сеансы не закрываются. Описание поведения, обслуживания
и обязательных настроек перед установкой прокси — в [защите входа](login-protection.md).

После этого изменения полный набор из 171 теста прошёл успешно,
неприменённых миграций и незаписанных изменений моделей нет. Проверка
действующего сайта вернула `ok`; новая зашифрованная копия проверена
восстановлением 30 таблиц и 2 медиа-файлов в отдельном окружении.

## Восстановление пароля

На странице входа доступна ссылка «Забыли пароль?». Пользователь указывает
email и получает одинаковое подтверждение независимо от того, зарегистрирован
ли этот адрес. Для активного аккаунта при доступном лимите отправляется одноразовая ссылка;
после открытия токен удаляется из адресной строки, а срок его действия — один
час. Новый пароль проверяется стандартными валидаторами Django. Приостановленные,
отключённые и приглашённые, но ещё не активированные аккаунты письма не получают.

Частота запросов ограничена: 5 запросов с подключения и 3 попытки доставки
на один email за 15 минут. Статус пользователя повторно проверяется при
применении ссылки; конкурентная смена пароля по одной ссылке защищена
транзакцией и блокировкой пользователя. Правила и ограничения описаны
в [восстановлении пароля](password-recovery.md).

Текущий локальный режим использует консольную доставку писем: содержимое выводится
в журнал контейнера, а внешняя SMTP-доставка ещё не настроена. Перед публичным
запуском требуется подключить SMTP или другой доверенный провайдер и проверить
DNS-аутентификацию домена (SPF, DKIM, DMARC).

После усиления восстановления пароля полный набор из 191 теста прошёл успешно
одним последовательным запуском, включая конкурирующие запросы на PostgreSQL.
Новая миграция для этого этапа не требуется.
