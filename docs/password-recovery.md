# Восстановление пароля

На странице входа доступна ссылка «Забыли пароль?». Пользователь указывает email
и видит одинаковое подтверждение для зарегистрированного, неизвестного,
приостановленного или отключённого аккаунта. Письмо отправляется только
активному пользователю с установленным паролем, если лимит писем не исчерпан.

## Защита от частых запросов

- Одно подключение может отправить 5 запросов за 15 минут. Учитываются также
  формы с некорректным email. Следующий запрос получает страницу ожидания
  со статусом `429` и числом секунд в `Retry-After`.
- Для одного email суммарно допускаются 3 попытки отправки письма за 15 минут,
  независимо от количества подключений. Следующие запросы показывают то же
  подтверждение, но письмо не отправляют. Пауза не раскрывает, зарегистрирован
  ли адрес; счётчик ведётся и для неизвестных или неактивных аккаунтов.
- Разный регистр email, эквивалентные Unicode-символы и пробелы по краям
  не создают отдельный лимит. При этом сама форма по-прежнему проверяет
  допустимость email.
- Просмотр страницы и отклонённые CSRF-защитой запросы не расходуют лимит.
  Отказы не продлевают 15-минутное окно. Ошибки доставки расходуют попытку:
  автоматической повторной отправки нет.
- Счётчики восстановления отделены от счётчиков обычного и административного
  входа. Ограничение писем не блокирует вход, не завершает сеансы, не меняет
  статус пользователя и не отзывает уже выданную действующую ссылку.

Счётчики общие для всех процессов сайта и хранятся в существующей служебной
таблице. HMAC-ключи не содержат открытых email или IP-адресов. Старые окна
удаляются ограниченными партиями по правилам из [защиты входа](login-protection.md).
Доверенным источником IP остаётся серверный `REMOTE_ADDR`; перед установкой
прокси необходимо настроить его корректную передачу.

При недоступности счётчиков письмо не отправляется; сайт возвращает общее
сообщение `503` и предлагает повторить через минуту. Ответы запросов и страницы
с токеном не кешируются. Для исходной ссылки с секретным токеном и ошибок
восстановления установлен `Referrer-Policy: no-referrer`. Для действительной
формы на адресе с маркером `set-password` используется `same-origin`:
секрет уже хранится в сеансе, а HTTPS-браузерам без заголовка Origin нужен
Referer для проверки CSRF. На внешние сайты Referer не передаётся.

20 сентября исправлен конфликт прежнего `no-referrer` с HTTPS-проверкой CSRF
на форме нового пароля. Регрессионный тест проверяет смену пароля без Origin
с адресом на порту 8443, а также отказ без CSRF-токена, без обоих заголовков
Origin/Referer и с посторонним Referer. Защита CSRF не отключалась.

## Одноразовая ссылка

Ссылка действует один час. После её открытия Django переносит токен в сеанс
браузера и перенаправляет на адрес без токена. При отправке нового пароля сайт
заново читает пользователя под блокировкой базы, проверяет текущий статус
и токен и сохраняет пароль в той же транзакции. Два браузера, одновременно
отправляющие одну ссылку, не могут по очереди перезаписать пароль: сработает
только первая успешная отправка.

Приостановленный, отключённый, приглашённый, неактивный пользователь или аккаунт
без установленного пароля не может воспользоваться ранее выданной ссылкой.
Повторное открытие уже заполненной формы также проверяет текущий статус.
Смена пароля, email, последний вход и истечение срока проверяются стандартным
токеном Django. Новый пароль проходит действующие валидаторы; ошибка заполнения
сама по себе не расходует ссылку.

После успешного восстановления предыдущие сеансы теряют авторизацию при
следующем обращении. Автоматический вход не выполняется: пользователь входит
с новым паролем через обычную форму.

Ожидание каждой блокировки базы при сохранении ограничено двумя секундами.
При ошибке базы транзакция смены пароля откатывается, а пользователь получает
общее сообщение без внутренних подробностей.

## Подключение почты

В `production.env` задайте сервер, порт, логин и пароль почтового провайдера,
а также подтверждённый адрес отправителя. Все имена параметров перечислены
в `production.env.example`; демонстрационные значения необходимо заменить.
Для STARTTLS обычно используется порт 587 с `DJANGO_EMAIL_USE_TLS=True` и
`DJANGO_EMAIL_USE_SSL=False`; для SSL — порт 465 и обратные значения флагов.
Точные параметры определяет провайдер. Оба флага одновременно включать нельзя.

`DJANGO_EMAIL_TIMEOUT=10` ограничивает ожидание сетевых операций SMTP.
Это тайм-аут отдельных операций, а не гарантия завершения всего запроса за
10 секунд: отправка остаётся синхронной.

Перед запуском выполните проверку production-настроек по
[инструкции эксплуатации](operations.md#режимы-запуска). Она работает без сети,
не отправляет письма и не печатает логин или пароль SMTP. Успешная проверка
означает только отсутствие обнаруженных ошибок конфигурации. Доставку,
SPF/DKIM/DMARC и восстановление через реальный HTTPS-домен нужно проверить
отдельно на адресе владельца. Изменение окружения применяется после пересоздания
web-контейнера.

### Выбран Gmail: подготовка 18 сентября 2026 года

Для первого запуска выбран личный ящик Gmail. Его адрес сохранён только в
локальном `secrets/gmail.env`; пароль приложения сохранён 18 сентября через
скрытое окно macOS, без вывода значения. Файл имеет права `600`, исключён
из Git и контекста сборки. Production читает его необязательным вторым env-файлом
**только для web**, поверх почтовых значений `production.env`. Обычный development
и PostgreSQL этот файл не получают. Пока пароля нет, почтовая deploy-проверка
возвращает `config.E008`; отправка не считается подключённой.

Параметры: `smtp.gmail.com`, порт `465`, SSL включён, STARTTLS выключен,
тайм-аут 10 секунд, логин и отправитель — один выбранный ящик.
Поддерживаемый Google альтернативный режим — порт `587` и STARTTLS.
[SMTP Google](https://developers.google.com/workspace/gmail/imap/imap-smtp).

В аккаунте отправителя нужно включить двухэтапную аутентификацию и создать
[пароль приложения](https://myaccount.google.com/apppasswords), например
«Семейный круг». Используется отдельный пароль приложения, а не основной пароль
Google. Если Google не предлагает эту возможность, проверить ограничения
аккаунта по [официальной справке](https://support.google.com/accounts/answer/185833?hl=ru);
не отключать защиту аккаунта для обхода ограничений.

После создания пароля его можно ввести локально в скрытом окне macOS:

```sh
python3 scripts/configure_gmail.py --sender YOUR_ACCOUNT@gmail.com --dialog
```

Заменить `YOUR_ACCOUNT@gmail.com` на выбранный адрес, уже указанный в локальном
файле. Без `--dialog` требуется интерактивный терминал со скрытым вводом.
Пароль не передаётся аргументом команды, не выводится в чат или журнал;
скрипт принимает 16 символов, допускает пробелы между группами, сохраняет файл
атомарно с правами `600` и отказывается перезаписывать уже заполненную или
изменённую конфигурацию. Отмена ввода не меняет файл. Команда сама не отправляет
писем, не меняет Google-аккаунт и не перезапускает сервер.

После сохранения нужны проверка авторизации SMTP, пробное письмо на согласованный
адрес и проверка получения. Не печатать `docker compose config` или окружение
контейнера целиком: после подключения они могут содержать пароль.
Применение к production выполняется при его развёртывании; отдельный файл Gmail
включается и в команды production-копирования, но его содержимое не попадает
в архив базы и медиа.

18 сентября прошли 13 почтовых/конфигурационных тестов без сети в одноразовом
контейнере и 38 тестов инструментов. Проверка Compose завершилась без ошибок.
Рабочий web был остановлен и для тестов не запускался. До сохранения пароля
на Mac и из отдельного контейнера оба SMTP-порта
не завершили соединение в пределах тайм-аута, до попытки авторизации.
После сохранения выполнена проверка подключения с последующей авторизацией:
она остановилась на тайм-ауте соединения, до передачи учётных данных.
Дополнительная проверка без пароля уточнила: по IPv4 порт 465 принимает TCP,
но TLS не завершается; порт 587 принимает TCP, но не присылает SMTP-приветствие.
По IPv6 соединение с 465 не установлено. Контрольное HTTPS-соединение с
`www.google.com:443` успешно, сертификат проверен. Авторизация Gmail пока
не подтверждена; письма не отправлялись, сервер не перезапускался.
Причина сетевой недоступности не установлена; шифрование и проверку сертификата
не отключали. После сообщения пользователя о смене сети повторены оба защищённых
варианта: на 465 — `TimeoutError`, на 587 — `SMTPServerDisconnected`, снова до
авторизации. Обычный HTTPS Google по-прежнему работает. Маршрут по умолчанию
и маршрут к IPv4 Gmail проходят через `utun6`: сетевой туннель сохраняется,
но его владелец и влияние на SMTP на тот момент не установлены.

19 сентября после сообщения об отключении VPN повторная проверка 465 и 587
остановилась с `OSError` до авторизации; маршрут по умолчанию проходит через
`utun8`. Проверка `scutil --nc list` вне ограниченной среды показала активные
подключения **«ЮБуст»** и **Tailscale**, а `scutil --nwi` — активный туннель
`utun8` и физический интерфейс `en0`. Ранее статусы `Disconnected` были получены
в ограниченной среде и не подтверждают отключение VPN: там же `--nwi` не смог
прочитать сетевое состояние. Следующий шаг — согласованно отключить именно
«ЮБуст» на время проверки, затем повторно проверить маршрут и Gmail.
Если без VPN недоступен чат, нужно отдельно согласовать локальную проверку,
не требующую связи с ассистентом во время отключения. Причинная связь между
VPN и отказом SMTP пока не доказана. Настройки сети не меняли, письма не отправляли.
Настройка Gmail ещё не означает, что доставка работает.

### Автономная проверка без связи с чатом

Подготовлен `scripts/check_gmail_offline.command`: запуск двойным щелчком на Mac
открывает локальное окно. Пользователь отключает «ЮБуст» и нажимает «Проверить»;
программа сама не меняет VPN. После завершения пользователь включает VPN обратно
и сообщает о готовности. Альтернатива из терминала:

```sh
python3 scripts/check_gmail_offline.py --dialog
```

Проверка использует сохранённые настройки локально, обращается только к
`smtp.gmail.com`, проверяет сертификат, пробует SSL 465 и при ошибке соединения
STARTTLS 587. После отказа авторизации повторный вход не выполняется. Отправки
писем нет. Проверка выполняется отдельным процессом с общим лимитом 45 секунд,
включая разрешение DNS; при превышении процесс останавливается.
Отчёт с уникальным именем сохраняется в `test-results/gmail-check/check-*.json`
с правами `600`. В нём нет логина, пароля или текста ответа SMTP; каталог исключён
из Git и контекста сборки. Проверку и результат нельзя приравнивать к подтверждению
доставки или подключению production. Подготовка проверена 10 тестами инструмента
и сохранения пароля без реального сетевого подключения.

19 сентября в 21:35 МСК автономная проверка на Mac завершилась успешно:
`status=authenticated`, порт `465`, без запасных попыток; сертификат проверен
штатным SSL-контекстом. Отчёт: `test-results/gmail-check/check-1mg6b6uv.json`.
Пользователь выполнял согласованную процедуру отключения VPN; сам инструмент
не фиксирует состояние VPN, поэтому отчёт подтверждает вход, а не причину
предыдущих сетевых отказов. Пароль приложения принят Gmail. Письма не отправлялись.
Следующий шаг — получить согласие на одно тестовое письмо на выбранный адрес,
проверить получение, затем подключение из production и ссылки восстановления.

Пользователь разрешил одно тестовое письмо на тот же выбранный Gmail-адрес.
Подготовлен `scripts/send_gmail_test.py --recipient ADDRESS`: локальное окно
позволяет отключить VPN и запустить отправку без связи с чатом. Локальный ярлык
с выбранным адресом находится в игнорируемом `secrets/send_gmail_test.command`.
Письмо имеет тему «Семейный круг — проверка почты», не содержит ссылок,
паролей или семейных данных. Принимается только адрес, совпадающий с сохранённым
логином; используется SSL 465 с проверкой сертификата. Общий лимит — 45 секунд.

Перед сетевой попыткой атомарно создаётся одноразовый маркер
`secrets/gmail-self-test-attempt.json`. Повторный запуск с существующим маркером
не отправляет письмо. После разрыва связи во время отправки результат считается
неизвестным; автоматических повторов нет. Не удалять маркер для повторной отправки
без проверки результата и нового согласия пользователя. Отчёт не содержит
учётных данных. `smtp_accepted` означает приём сервером Gmail, а не подтверждённое
получение во «Входящих». Реальную доставку подтверждает пользователь.
14 тестов отправки, автономного входа и сохранения пароля прошли без реальной сети.

19 сентября в 21:39 МСК одно согласованное тестовое письмо принято Gmail:
`secrets/gmail-self-test-attempt.json` содержит `status=smtp_accepted`.
Пользователь подтвердил получение письма. Таким образом, вход и реальная доставка
с Mac проверены. Одноразовый маркер сохранён; повторной отправки не требуется.
Это не подтверждает подключение production, отправку приглашений из самого сайта,
работу публичных ссылок или SMTP при включённом VPN — эти проверки остаются.

Последующая проверка: macOS показывает активные Sota Connect и Tailscale,
«ЮБуст» отключён. В одноразовом Docker-контейнере с сохранённым Gmail env-файлом
штатный SMTP backend Django успешно открыл соединение и авторизовался.
Использована новая команда `check_email_connection`, без отправки сообщений.
Контейнер не подключался к семейной базе, не получал семейные файлы и удалён
после проверки. Это подтверждает работоспособность подключения при текущем
Sota Connect, но не исправляет маршрутизацию «ЮБуст» и не гарантирует её в будущем.
19 тестов почтовых настроек и новой команды прошли в контейнере без сети.

После развёртывания production проверку его фактических настроек можно повторить:

```sh
docker compose -p family-production -f compose.production.yaml exec -T web python manage.py check_email_connection
```

Команда отвергает консольную почту и неверные режимы шифрования, задаёт тайм-аут
сетевых операций 10 секунд, не отправляет писем и не выводит текст исключений
провайдера. Успешный вход не заменяет проверку доставки приглашения.

## Текущие ограничения

В локальном development-режиме письма выводятся в журнал контейнера.
Отдельная отправка с Mac через Gmail проверена реальным тестовым письмом;
Production-сервер отдельно запущен на loopback-порту 18080; его фактическое
SMTP-подключение проверено командой `check_email_connection`, без новых писем.
Публичный HTTPS-маршрут и приглашения из этой среды ещё не проверены;
семейные данные в неё не перенесены.
Для публичного запуска потребуется подключить почтовый сервис и проверить
защищённые ссылки с корректным доменом.

Отправка письма пока синхронная: одинаковый текст ответа не гарантирует одинаковое
время ответа для существующего и неизвестного email. Отдельной очереди доставки
и автоматического уведомления о смене пароля пока нет.

Лимит на email временно может задержать новое письмо после чужих запросов;
используйте уже полученную действующую ссылку или подождите окончания окна.
При возврате аккаунта из приостановленного в активное состояние старая ссылка
может снова работать в пределах своего часа, если пароль, email и последний
вход не изменились. Текущая проверка статуса не является постоянным отзывом
всех ранее выданных ссылок.

## Проверка

```sh
docker compose exec -T web python manage.py test accounts.test_password_reset accounts.test_password_reset_limits accounts.test_password_reset_security --keepdb
```

Не запускайте два набора тестов одновременно с одной тестовой базой.
Проверки покрывают лимиты, ошибки, CSRF, истечение ссылки, смену статуса/email,
инвалидацию сеансов и конкурентное применение ссылки на PostgreSQL.
Все 25 проверок восстановления входят в успешно пройденный полный набор
из 191 теста проекта.

Решение опирается на [стандартное восстановление пароля Django](https://docs.djangoproject.com/en/6.1/topics/auth/default/#django.contrib.auth.views.PasswordResetConfirmView)
и меры против массовых запросов из [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
Пороги 5 и 3 за 15 минут — правила этого проекта.
